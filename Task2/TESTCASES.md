Позитивные сценарии
TC‑01. Создание объявления (успешный сценарий)
Цель: проверить успешное создание объявления
Метод: POST /api/ads
Данные: валидные name, price, sellerId
Ожидаемый результат: статус 201 Created, в ответе id созданного объявления
Техника тест‑дизайна: эквивалентное разбиение (валидные данные)

TC‑02. Получение объявления по ID (успешный сценарий)
Цель: проверить получение объявления по корректному ID
Метод: GET /api/ads/{id}
Данные: ID существующего объявления
Ожидаемый результат: статус 200 OK, в ответе данные объявления, совпадающие с отправленными при создании
Техника: эквивалентное разбиение

TC‑03. Получение объявлений по sellerId (успешный сценарий)
Цель: проверить получение списка объявлений продавца
Метод: GET /api/sellers/{sellerId}/ads
Данные: sellerId с существующими объявлениями
Ожидаемый результат: статус 200 OK, в ответе массив объявлений указанного продавца
Техника: эквивалентное разбиение

TC‑04. Получение статистики по itemId (успешный сценарий)
Цель: проверить получение статистики по корректному itemId
Метод: GET /api/ads/{itemId}/statistics
Данные: itemId существующего объявления
Ожидаемый результат: статус 200 OK, в ответе объект статистики
Техника: эквивалентное разбиение

Корнер‑кейсы
TC‑10. Идемпотентность создания объявления
Цель: проверить, что повторные запросы с одинаковыми данными создают разные объявления
Метод: POST /api/ads (несколько раз с одними данными)
Данные: одинаковые name, price, sellerId
Ожидаемый результат: каждый запрос возвращает 201 Created и уникальный id
Техника: проверка идемпотентности

TC‑11. Дублирование данных
Цель: проверить возможность создания объявлений с одинаковыми name, price, sellerId
Метод: POST /api/ads (два раза с одинаковыми данными)
Данные: идентичные name, price, sellerId
Ожидаемый результат: оба запроса возвращают 201 Created с разными id
Техника: проверка бизнес‑логики

TC‑12. Высокая нагрузка (нефункциональная проверка)
Цель: проверить стабильность API при множественных запросах
Метод: GET /api/ads/{id} (100 запросов подряд)
Данные: ID одного объявления
Ожидаемый результат: все запросы возвращают 200 OK без ошибок и таймаутов
Техника: нагрузочное тестирование

TC‑13. Проверка времени ответа (нефункциональная)
Цель: проверить время ответа API
Метод: любой эндпоинт
Данные: валидные параметры
Ожидаемый результат: время ответа < 500 мс
Техника: производительность

TC‑14. Проверка заголовков безопасности
Цель: убедиться, что API возвращает необходимые security‑заголовки
Метод: любой запрос
Данные: любые валидные параметры
Ожидаемый результат: в ответе присутствуют заголовки X-Content-Type-Options, X-Frame-Options и т. д.
Техника: безопасность

Дополнительные проверки
TC‑15. Валидация формата данных
Цель: проверить валидацию полей (длина name, диапазон price)

Техника: граничные значения
